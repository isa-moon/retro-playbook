# 体检

目标：让经验库保持「每条都是现役、可信、能被找到」。过期的教训比没有更糟，因为它会被自信地执行。

原则：**合并优于追加，归档优于保留**（归档不是删除，随时可以找回）。

## 1. 机器检查（只读）

```bash
python3 scripts/lessons.py lint
```

lint 能查的：

| 问题 | 含义 | 默认处置 |
|---|---|---|
| 缺字段 | 必填字段为空 | 补；补不出来说明这条本来就没想清楚 → 改写或归档 |
| 空话 | 标题或 do 里有「加强沟通」「提前准备」之类 | 按六项检验改写成具体动作；改不出来 → 归档 |
| 触发太泛 | when 太短，或以「下次」「以后」开头 | 改成可观察的信号 |
| 无证据 | 正文缺「发生了什么」 | 去 `source` 指向的复盘记录里补；没有来源 → 置信度降为「存疑」 |
| 到期复核 | 过了 review_by | 问用户：现在还成立吗？成立就顺延，不成立就证伪或改写 |
| 僵尸 | 半年没被唤醒过 | 多半是 when 写成了别人搜不到的样子 → 改 when；确实不重要 → 归档 |
| 有害 | 误导次数 ≥ 有用次数 | 看误导记录：收窄 scope、改写 do，或标「已证伪」后归档 |
| 可升级 | 单次观察但已多次有用 | 问用户是否升为「多次验证」 |
| 疑似重复 | 标题和 when 相似 | 读两条全文再判断，见第 3 步 |

## 2. 人工检查（lint 查不了的）

通读 INDEX.md，找：

- **矛盾**：两条的 when 重叠、do 相反。一般不是谁错了，而是适用条件不同 → 各自补 scope，把条件拆开。拆不开就把两边证据摆给用户，让用户裁决。
- **被新规则淘汰的**：平台、法规、价格这类教训，结合你知道的近期变化判断是否仍然成立；不确定就标「到期复核」，交给用户。
- **一类问题被拆成了很多条**：比如五条都在讲「某个审核节点没有进排期」→ 合并成一条更上位的教训，原条目归档并注明「合并入 Lxxxx」。

## 3. 合并怎么做

1. 保留编号更早的一条（它的唤醒和验证记录更多）。
2. 把另一条的证据追加进「发生了什么」，注明来源项目。
3. 计数字段相加，手工改 frontmatter；在「验证记录」里注明「合并自 Lxxxx」。
4. 用两条的共同证据重新判断 when、do、scope、confidence；两个独立项目都验证过的可以升「多次验证」。
5. 被合并的一条：`lessons.py archive Lxxxx --reason "合并入 Lyyyy"`。

## 4. 先预览，确认后执行

把全部改动列成一张表给用户看，确认后再执行：

| 编号 | 问题 | 处置 | 改动内容 |
|---|---|---|---|

可以只确认一部分。执行完运行 `lessons.py index`，再跑一次 `lessons.py lint`，确认问题数下降。

## 汇报模板

```
## 经验库体检：<日期>
现役 N 条 → M 条（合并 a · 归档 b · 改写 c · 顺延复核 d）
- <编号> <处置>：<一句原因>
仍待你决定：<矛盾、到期但你没回答的>
下次建议体检：<建议日期，比如 3 个月后，或再积累 10 条之后>
```
