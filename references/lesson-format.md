# 教训文件格式

一条教训一个文件，放在 `<经验库>/教训/`，文件名 `L0001-短标题.md`。编号用 `lessons.py next-id` 取，不要自己猜。

## 模板

```markdown
---
id: L0001
title: 一句话说清这条教训（≤30 字，能当提醒看）
when: 未来哪个可观察的时刻/信号出现时适用
do: 到那时具体做什么（或不做什么），能被检查有没有做
scope: 什么情况下不适用（没有就写「暂未发现」）
type: 避坑            # 避坑 | 保持 | 基准 | 情报（见下方「四种类型」）
tags: 直播电商, 价格, 上播前检查
confidence: 单次观察   # 单次观察 | 多次验证 | 存疑 | 已证伪
cost: 这次付出的代价或带来的收益，尽量量化
source: 复盘/2026-06-20-某零食品牌618直播.md
created: 2026-06-20
review_by: 2026-12-20  # 可空，见下方「复核期」
recalled: 0
applied: 0
helped: 0
hurt: 0
---

## 发生了什么（事实）
带数字、原话、文件出处。只写能被核对的东西。

## 为什么（推断）
你和用户对原因的判断。写明依据，以及排除了哪些别的解释、还有哪些没排除。

## 验证记录
（由 `lessons.py log` 自动追加，不要手写计数）
```

## 四种类型

| 类型 | 是什么 | 例 |
|---|---|---|
| 避坑 | 这次付出过代价、下次在某个时刻要换做法 | 券叠加没实测，到手价击穿底价 |
| 保持 | 做对了、下次要继续的做法。没有这类，库只会教人保守 | 开播前按真实弹幕问题彩排 |
| 基准 | **自己的**数据参照：某品类/量级/渠道在什么条件下的实际区间。来自你们的结案数据，不是行业报告 | 零食类腰部主播坑位费 ROI 在 1.2–1.8，样本 3 场 |
| 情报 | 某个具体合作方、平台、审核方的真实脾性和节奏 | 某平台直播间价格复核通常在开播后 30 分钟内触发 |

基准和情报是最不可替代的两类：模型再强也不可能知道你们的历史数据和合作方的脾性。

## 字段怎么写

| 字段 | 要求 | 反例 → 正例 |
|---|---|---|
| `when` | 下个项目里**某人在某一步看到某个信号**时能对上。写信号，不写阶段名 | 「下次直播时」→「直播间同时挂店铺券和平台券（或满减）时」 |
| `do` | 动词开头，有对象，有时点；别人能检查「做了没」 | 「注意优惠设置」→「开播前 2 小时用测试账号对每个链接实际下单到支付页，截图到手价，对照底价表签字后才开播」 |
| `scope` | 防止下次被过度套用 | 「只挂单一优惠、且平台无叠加活动时可简化为抽查」 |
| `cost` | 让下次的人掂量值不值得照做 | 「券叠加后到手价低于成本 12 元，前 20 分钟卖出 1300 单，亏损约 1.6 万」 |
| `confidence` | 一次项目只能是「单次观察」。被另一个项目再次验证有效才升「多次验证」；被反例推翻标「已证伪」，再由体检归档 | |
| `type: 保持` | 做对了的事也要入库，否则库只会教人保守 | 「开播前一天和主播按真实弹幕问题彩排 30 分钟，本场答疑类弹幕回复率 90%」 |

## 复核期（review_by）

教训会过期，过期的教训比没有更糟：它会被自信地执行。

| 教训依赖的东西 | 建议复核期 |
|---|---|
| 平台规则、政策法规、价格行情、算法机制 | 6 个月 |
| 特定合作方（某机构、某客户、某供应商）或某类合作方的普遍行为 | 12 个月 |
| 团队内部流程、通用协作机制 | 可不设 |

## 对事不对人

经验库可能被团队共享。不写个人责任，写机制缺口：

- 「运营小王没检查券」→「开播前没有『实际下单验证到手价』这一步」
- 「供应商不靠谱」→「样品确认后到大货发出前没有抽检节点」
