# 复盘入库

目标：从一个结束（或出事）的项目里，提炼出**少量、下次会在决策点上改变动作**的教训，并让它们进库、能被找到。复盘报告是副产品，不是交付物本身。

## 0. 先回填，再复盘

先 `lessons.py where` 确认经验库位置（未初始化就按 SKILL.md「经验库在哪」建库；新库自然没有回填，直接跳到第 1 步）。再查本项目开工时有没有唤醒过教训：

```bash
python3 scripts/lessons.py trail 项目名     # 唤醒时 log 写入的项目名；不确定就多试几个叫法
```

对每条被唤醒的教训问清：采用了吗？有用吗？然后 `lessons.py log ID helped|hurt --project 项目名 --note 一句话`。没采用的不记 helped/hurt，但要问一句「为什么没采用」——答案常常就是一条新教训，或者说明旧教训的 `when`/`do` 写得不对。

**如果这次踩的坑库里已经有**，这比新坑更重要：说明闭环断在唤醒或执行环节。复盘的重点应转为「为什么有教训却没用上」，而不是再写一条重复的。

## 1. 读材料，搭骨架

先读用户给的一切：brief、方案、排期、数据表、聊天记录、会议纪要、结案报告。能从材料里查到的，不问用户。

搭三样东西（写给自己用，最后放进复盘记录）：

1. **目标 vs 结果**：每个 KPI 的目标、实际、差距。超额完成的也列出来。
2. **计划 vs 实际时间线**：哪些节点滑了、滑了多少、谁先滑的（事件，不是人）。
3. **材料缺口**：哪些判断缺数据。不要用猜测补缺口，列出来问。

## 2. 找信号：教训藏在哪

按信号强度从高到低扫：

| 信号 | 为什么值得看 |
|---|---|
| 返工、重做、推倒重来 | 代价最具体，原因通常最可操作 |
| 计划和实际的偏差 | 每一次滑期背后都有一个本可以更早被发现的信号 |
| 「没想到」的时刻 | 预期错了，就是认知该更新的地方 |
| 临时拍板的决策（好的和坏的） | 好的要变成「保持」，坏的要找出当时缺什么信息 |
| KPI 未达成，**也包括超额达成** | 超额同样说明预期模型不准 |
| 复盘会上的「大家觉得」 | 共识最容易是空话，最需要追问 |
| 被「先别声张」「结案再看」压下的事 | 往往是风险，也可能涉及合同、结算或合规，必须提给用户 |

领域相关的高信号区见 `marketing.md`（营销项目）。其它领域按同样思路自己找。

## 3. 追问

每轮最多 3 个问题，按信息量排序。每个问题都带上你的初步判断，让用户纠正，而不是让用户从零回答：

> 我看到第二场直播的样品是开播当天中午才到的，采购单是开播前 3 天才下的。我的判断是「样品到货时间没有进排期，没人在倒推节点上卡它」。是这样吗？还是另有原因？

问题库（挑合适的，不要全问）：

- **时点**：「如果重来，你会在哪一天、哪一步做不同的决定？」——答案就是 `when` 的原料。
- **信息**：「当时知道什么？本可以在什么时候、用什么方式知道？」——区分「判断错了」和「信息不够」。
- **运气**：「结果好（或坏）是因为决策，还是因为运气/外部变化？」——结果好不等于决策好。
- **混杂**：「这个结果还有别的解释吗？」——见下方「归因陷阱」。
- **重复**：「这种事以前出现过吗？」——出现过就先查库。
- **代价**：「这件事具体让我们多花了什么？」——时间、钱、效果，尽量要数字。

用户不想答或说「你看着办」时：按你的判断起草，在汇报里把这条标为「AI 推断，未经你确认」，入库时 `confidence: 存疑`。

## 4. 归因陷阱（最常见的错）

起草每条教训前，检查它是不是掉进了这些坑：

1. **混杂因素**：A 组比 B 组好，但 A、B 在另一个维度上也不同。例：「晚场直播 GMV 比早场高 2 倍，以后多排晚场」——先看晚场是不是恰好挂了主推爆品或更大的券。如果是，结论应该是关于货品和优惠，而不是时段。凡是「X 类效果更好」的结论，都先把表现差的那几个单独拎出来，看它们还有什么共同点。
2. **样本量为一**：一个项目里的对比只能是「单次观察」，写成规律就是过度推广。
3. **结果论**：结果好就认为当时决策对。问：如果运气差一点，这个决策还站得住吗？
4. **事后诸葛亮**：「早该知道」——当时真的有渠道知道吗？没有的话，教训是「建一个获得这个信息的渠道」，而不是「要更有远见」。
5. **把推断当事实**：某人的猜测（「可能是因为……」）只能写进「为什么（推断）」，并注明是谁的推断、依据是什么、缺什么数据验证。
6. **归咎于人**：写成机制缺口。见 `lesson-format.md` 的「对事不对人」。

## 5. 起草候选教训，自检六项

对每条候选，按 SKILL.md 的六项检验自检（触发点 / 动作 / 证据 / 归因 / 边界 / 下次 AI 自己想不到）。过不了的，要么改写，要么不入库。

特别留意第六项。复盘时很容易顺手写出一长串「最佳实践」，其中大部分下次让 AI 写方案时它自己就会提。要留下的是只有这个团队才知道的东西：

- **基准**：从这次数据里算出来的、下次做计划能直接参照的数字（注明样本量和条件）。
- **情报**：具体客户、机构、平台、审核方这次表现出来的节奏和脾性。
- **代价大的具体坑**：写成具体对象、具体时点、具体代价的形态，而不是一条通用原则。

给用户看的是一张表：

| # | 类型 | 什么时候（when） | 做什么（do） | 证据一句话 | 置信度 | 建议 |
|---|---|---|---|---|---|---|

外加一节「**观察到但不建议入库的**」，每条一句原因（如「只是这次的偶发」「是常识，不需要库提醒」「证据不足，先记在复盘记录里」）。这一节说明你筛过，用户可以把某条捞回来。

数量：一次复盘通常 2–4 条，最多 5 条。超过 5 条说明还没筛。

拆还是合：**一条教训对应一个 when。**两件事会在下次不同的时刻、被不同的人想起（比如「任何功效类卖点都要先过法务」和「这个客户的法务审核要两周」），就拆成两条；会在同一时刻想起的，合成一条，`type` 按它最主要的价值定。基准和情报类的 `do` 写「下次怎么用这个数字或这条情报」。

## 6. 查重，决定新建还是合并

对每条候选跑 `lessons.py search <when 的关键词> --tags <标签>`。

- 有实质相同的旧教训 → **合并**：在旧文件的「发生了什么」里追加本次证据，更新 `cost`；如果这次照做了并且有效，用 `log helped`；如果这次是又踩了一次，说明旧条目的 `when` 或 `do` 有问题，一并改写。
- 部分重叠 → 判断能不能通过收窄 `scope` 区分；不能就合并。
- 和旧教训**矛盾** → 不要静默共存。向用户说明两条各自的证据，通常的解法是按 `scope` 拆开适用条件。

把「新建 N 条 / 合并进 Lxxxx / 改写 Lxxxx」的计划给用户看，确认后再写。

## 7. 写入

1. 复盘记录写进 `<经验库>/复盘/YYYY-MM-DD-项目名.md`（日期用复盘当天，项目周期写在正文里）：目标 vs 结果、时间线、材料缺口、全部候选（含未入库的及原因）、用户的回答要点。
2. 新教训按 `lesson-format.md` 写进 `教训/`，编号用 `lessons.py next-id`，`source` 指向上面的复盘记录。
3. `lessons.py index` 重建目录，`lessons.py lint` 确认没有新增「缺字段」「空话」「触发太泛」。lint 报的是本次新写的，就改到通过；报的是旧条目，列进汇报的「顺手发现」，不在这次擅自改。

## 汇报模板

```
## 复盘完成：<项目名>

**目标 vs 结果**：<一行一个 KPI，标达成/未达成>

**入库**（新建 N · 合并 M）
- L0012 [避坑] <标题>
  什么时候：<when> → 做什么：<do>（单次观察）
- L0005 [合并] <标题>：追加本次证据，<改了什么>

**回填**：L0003 有用 / L0007 采用但误导（原因）/ L0009 未采用（原因）

**没入库的观察**：<每条一句原因>

**待你确认**：<推断未经确认的、涉及合同/结算/合规需要你决定的>

**顺手发现**：<lint 报的旧条目问题，建议做一次体检>
```
