# 评分表：澄言案例 · 复盘入库

同一份 fixture，分别跑「无 skill 基线」和「装 skill」，按下表打分。分析质量（重算 KPI、找混杂、发现刷量）基线已经很好，不是本 skill 要证明的东西；重点看**沉淀**。

| # | 检查项 | 通过标准 |
|---|---|---|
| 1 | 入库数量 | 新教训 2–5 条（不是一长串清单） |
| 2 | 每条有可观察的 when | 不出现「下次项目」「以后」这类触发 |
| 3 | 每条 do 可检查 | lint 无「空话」 |
| 4 | 事实 / 推断分开 | 正文有「发生了什么（事实）」和「为什么（推断）」 |
| 5 | 混杂识别 | 「多用腰部」没有被直接写成教训；或者已拆出「改稿/延期」这个混杂因素 |
| 6 | 不发明数字 | 教训中的阈值要么来自数据，要么标了「建议值，未验证」 |
| 7 | 有基准或情报 | 至少一条 `type: 基准` 或 `情报`（如：本团队护肤腰部按时上线的 CPM 区间、澄言法务审核实际周期） |
| 8 | 有保持类 | 至少一条 `type: 保持`（如：自然流好的内容加热投流），或说明了为什么没有 |
| 9 | 置信度诚实 | 全部为「单次观察」或「存疑」，没有「多次验证」 |
| 10 | 被压下的风险 | 刷量的处置（是否告知客户、找机构追责）单列在「待你确认」 |
| 11 | 可追溯 | 有 `复盘/` 记录，教训的 source 指向它 |
| 12 | 体检通过 | 对本次新写的条目，`lessons.py lint` 无缺字段、空话、触发太泛、无证据 |
| 13 | 未入库观察 | 列出了筛掉的候选及原因 |
| 14 | 对事不对人 | 教训里不出现「小林」「阿强」之类的个人归责 |
